# Contributing

## CLI (`ocforge/`)

```bash
pip install -e ".[dev]"
ruff check ocforge tests
pytest -q
```

Both run in CI on every push and PR (`.github/workflows/ci.yml`) — a red
check there means something's actually broken, not just style nitpicking.

A few conventions the existing code follows, worth matching:

- Every hardware-driven decision traces back to a specific Dortania guide
  page or a real device report — not a guess. If you're not sure a value is
  right, say so in a comment rather than presenting it as confirmed.
- New generation/hardware support gets a test alongside it in `tests/`,
  ideally one that would have caught the bug you're fixing if it existed
  before.
- Prefer fixing the root cause over adding a special case, but when a
  special case really is the correct fix (a specific board's quirk, a
  specific generation's exception), a one-line comment on *why* saves the
  next person from "fixing" it back.

## GUI (`gui/`)

```bash
cd gui
flutter create --platforms=windows,macos,linux --project-name ocforge_gui .
flutter analyze --no-fatal-infos --no-fatal-warnings
flutter run -d windows   # or macos / linux
```

Only `lib/`, `pubspec.yaml`, and `analysis_options.yaml` are tracked — the
platform folders (`windows/`, `macos/`, `linux/`) are regenerated by
`flutter create`, both in CI and above. Don't commit them.

No pub dependencies beyond the Flutter SDK itself — this is deliberate (see
`controller.dart`'s comment on why), so a PR adding one should have a real
reason it can't be done with `dart:io`/`dart:convert` directly.

## Docs

`README.md`, `SupportedDevice.md`, and `docs/index.html` (the install guide,
also served live via GitHub Pages) are all fair game to edit directly —
that's exactly how they've grown so far. If you're adding a device to
`SupportedDevice.md`, include the CPU generation/model and what actually
worked or didn't; "it worked" without specifics helps the next person less
than you'd think.

## Reporting a bug instead of fixing one

`ocforge report` (CLI), the bug icon in the GUI's nav rail, or `/report` in
the Discord server all open a pre-filled GitHub issue — your version and
hardware are already in it, you just describe what happened.

Found a security issue instead? See [SECURITY.md](SECURITY.md) — please
don't file those as a public issue.
